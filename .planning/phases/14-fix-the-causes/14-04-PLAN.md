## Flagged assumptions

- D-07's gate says "mode 4 (M4=1)". Per RESEARCH premise check 3, `mode4` can never be a faulting class, so the gate is read as any M4=1 class (`mode4`, `invalid`, `sms2only`). RESEARCH premise check 3 also says vdp_supported matches SMS-VDP 2.5 today (8, 10, 12 everywhere; 11, 14, 15 on SMS2 and Game Gear; 9 and 13 nowhere), so a literal decode fix is expected to be unnecessary; the check is still run and recorded.
- D-07 and D-10 overlap for an M4=1 row on a family mapper. The decode check runs first (D-07); if the decode agrees with SMS-VDP 2.5, the row is D-10's fast-boot or mapper question.
- D-04's trigger, "a whole board family's exact-register writes", is read as 5 or more rows of ranks 3 and 7 together in one `reg-*` class. 5 is the phase's group threshold, and it is an assumption, not part of D-04: Task 1 writes it as its own line in the outcomes note's decision table ("D-04 trigger threshold: 5 rows in one reg-* class of ranks 3 and 7 (assumption; the owner can change the figure)"), and the `D-04 trigger:` line prints every reg-* class count, including classes of 1 to 4 rows marked `below threshold`, so a family the figure leaves out is visible in the record. Plan 08 lists any below-threshold reg-* class with rows as a seed candidate in SEED-016.
- D-04 offers "a table row or a header rule". The board table keys on the image SHA-1 (`src/cartdb.inc`, looked up by `cogmaster__cartdb_find` in src/cartdb.h), so a table row would be keyed on a dump-derived digest, which D-13 and the counts-only rule forbid. The header rule is the route this plan takes; a family whose rows share no header property needs evidence this phase does not have and goes to the single gap round.
- The fast-boot state (src/boot.c) has no planned fixture shape; a trace that points at it is new evidence for the gap round, stated in the note.
