## Design notes the executor must keep

- **VRAM map for `g2_switch` (D-04).** The image starts each frame in mode 4 and switches to Graphics II with one R0
  write (R0 `$16` to `$12`, nibble 10 to nibble 2) from the line-interrupt handler, then restores mode 4 in VBlank. The
  shared R2, R3, R4 and R5 must suit both modes without overlap: Graphics II colour at `$0000` (R3 `$7F`), patterns at
  `$2000` (R4 `$07`), legacy names at `$3C00` (R2 `$0F`, so mode 4 reads names from `$3800`), SAT at `$3F00` (R5 `$7E`,
  the same base in both modes) holding Y `$D0` at entry 0, and the mode 4 portion drawing only a zero tile at `$1800`
  (tile `$C0`) from name rows 0 to 11 (`$3800`-`$3AFF`), so the switch line must be before line 96. The lines wholly before
  the switch line are closed form (CRAM entry 0 everywhere), the lines wholly after are the Graphics II oracle, and the
  switch line itself is pinned by hash only in plan 05. The switch line is the line after the line-interrupt line
  (line /INT at tick 608, handler write early in the next line, video.md timing model); legacy.c records it as a constant
  with that reasoning.
- **No sprites in `legacy_modes_*`.** Every legacy_modes image holds Y `$D0` at SAT entry 0 (it terminates in mode 4 at
  192 lines and in legacy modes), so plan 07's sprite engine cannot move their hashes.
- **`g2_late` (MODE-06):** boots in mode 4 at 192 lines with a closed-form screen and enters Graphics II after frame 600
  (counted in RAM by the VBlank handler); legacy.c compares a frame after the switch (for example frame 610).
- **Generated scenes (D-23, research Pitfall 11).** Name, pattern and colour bytes are generated by loops in the ROM from
  formulas in the tile-index domain written once in a comment block shared by the asm and legacy.c (for example name byte
  `(col + 32*row) & 255`, Graphics I pattern byte `(tile*7 + row*29) & 255`, colour bytes chosen so that a zero high nibble
  and a zero low nibble each occur, so nibble 0 shows the backdrop). The ROM uses TI layout addresses; the oracle never does
  address arithmetic. No `.DB` run of 256 or more hex-only bytes (the hygiene tripwire).
- **Profiles.** sms1, sms2 and gg-in-SMS-mode (`--machine gg --video-mode sms`), NTSC-U; native Game Gear is not run.
  The images write CRAM entries 16 to 31 with a known table that differs from the fixed palette, so the Game Gear oracle
  (CRAM 16+n, D-10) and the SMS oracle (fixed palette) give different digests.
- **`g2_masked`:** one (R3, R4) pair where both masks bite on SMS1 (for example R3 `$9F`, R4 `$00`), so the SMS1 digest
  differs from SMS2 and Game Gear; legacy.c's literal self-check asserts that the two digests differ.
- **Sprite scenarios (legacy_sprites).** Graphics I with all-zero patterns (background is the backdrop); one scenario per
  fixed number of frames, SAT written in VBlank; the image never reads `$BF` except the one recorded read per scenario
  (wait for VBlank by polling the V counter at `$7E`, so flags are not cleared early). The tail-read row (research Open
  Question 1): five Y matches on exactly one line L+1 (four sprites starting at L+1, a fifth ending at L+1) and a status
  read placed after the tick-600 scan of line L and before dot 0 of L+1, from a line-interrupt handler for line L-1 with a
  calibrated delay, recording the H counter (`$7F`, read live because the H counter is not held) next to it; the
  frame-end read must report bit 6 and the fifth's SAT index. The row is mandatory: adjust the delay loop until the
  recorded H counter maps to ticks 600 to 683 of line L (the core is deterministic, so one calibration holds; map the H
  counter to ticks with the H counter table in docs/hardware/video.md, the same mapping `cogmaster__vdp_hcount_at`
  implements). Calibrate in this plan: the read's timing and the H counter do not depend on the sprite engine, so
  `build/ci/cogmaster-run build/ci/fixtures/legacy_sprites.sms --mailbox` already prints the record. The H counter's
  expected value is the inclusive range of H counter values for ticks 600 to 683, named `TAIL_HCOUNT_LO` and
  `TAIL_HCOUNT_HI` in legacy.c with that derivation in their comment; its CSV row uses the judge's `lo-hi` form and cites
  them. Plan 07's in-process `vdp.legacy.sprites.fifth_carry` is a second proof, not a replacement.
- **Y rows (D-14, research Open Question 2):** a 16x16 magnified sprite at Y `$E8` shows pattern rows 11 to 15 on lines 0
  to 8; at Y `$E0` line 0 shows pattern row 15 (the row that separates `>= $E0` from `> $E0`).
