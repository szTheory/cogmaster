## Phase Boundary

## Resolved conflicts (decision, evidence, reason)

1. **Aim encoding, persistence and range.** Decision: on a phaser port `x1,y1` (port 1) or `x2,y2` (port 2) are an ABSOLUTE aim in **1-based field dots**: x 1..256, y 1..240 (the dot is `x - 1`, `y - 1`); `0 0` means no aim. The call is LAST-WINS (never summed). `set_input` keeps the existing range check (each axis -32767..32767, else `ERR_ARGUMENT`) and then CANONICALISES a phaser axis pair before storing: if either coordinate is outside 1..256 and 1..240 respectively, the pair is stored as `0 0` (a state, not an error and not a clamp: an aim that is not a field dot senses nothing and is never moved to an edge pixel). The row bound is 240 whatever the current mode; a row beyond the current height simply senses nothing. A device change on a port restarts its axes at 0 (the existing line stays). Persistence: `ports_frame` zeroes the pending and active axes of a port only when that port's device is not the phaser, so the aim survives frames, the frame-start copy gives `m->input` the aim in force, and the sensor never reads `pending_input`. Soft reset keeps the pending aim (as it keeps Sports Pad deltas), load and power zero it (`instance.c:239`), so a fresh, reset or loaded instance is parked. Evidence and reason: the product lens's 1-based zero (a zeroed `cogmaster_input`, every 35-byte script line, every tag-32 caller and every fuzz seed means "no aim", so a zeroed input can never point the gun at the lit border corner) is adopted because it makes GUN-02 hold by construction; the security lens's int32 concern is real (`axis_ok` admits +-32767, so `dx*dx + dy*dy` could reach 2.2e9) but is solved by canonicalising rather than clamping: a stored aim has `|dx|, |dy| <= 256` so the squared sum is below 2^17 and nothing overflows; this also reconciles PITFALLS 9 ("offscreen is its own state, not clamped") with the security lens's clamp band (the band is replaced by the single parked state, so nothing is stored that could alias an edge pixel). The 1-based zero gives up one real aim, dot -1 (a disc centred just left of the field that would still light dots 0 to 5); no host sends it (hosts send "off screen" or a dot inside the picture) and it is stated in `docs/controllers.md`. Architecture's "reuse `x1..y2`, no new field" is adopted: the struct stays 48 bytes, `FIRST_SIZE_INPUT` 32 and every Phase 8 size test are untouched.
   State encoding of aim, three places, all visited: `pending_x1..y2` and `active_x1..y2` hold the canonical pair for a phaser port (0..256 and 0..240, both zero or both non-zero) and stay 0..0 (active) or the existing rule (pending) for every other device; the port block holds a per-picture SNAPSHOT of the aim (decision 5) so the scan of a 224 or 240 line picture that straddles two frame windows uses the aim it started with and never a later frame's.

The Mark III is no profile here. Consequence: "SMS and Game Gear crops" in GUN-03 cannot be a reachable run. The crop mapping is a PURE HELPER over the rectangle of the last frame (`cogmaster_frame` `x y w h`, which the libretro adapter already receives), tested with SMS rectangles (256 by 192, 224, 240 at 0,0) and Game Gear rectangles (160 by 144 at 48,24 and 48,40); the runner needs no mapping call because every machine that can hold a phaser has its crop at 0,0, so a script aim IS the field dot, and the fixture proves it (a script aim at the lit square's picture position latches the expected X; the same aim 16 dots off fails). 3. **Edge rule, TH level model, and what is unmeasured.** Decision: KEEP the shipped rising-edge latch: `th_changed` latches when the effective TH of either port goes low to high, and the sensor feeds the same function, so the latch happens at the tick the sensor RELEASES TH. TH on `$DD` b6 (port 1) and b7 (port 2) reads LOW while the sensor sees light, only when that port's TH is an INPUT (`$3F` b1 for port 1, b3 for port 2; an output TH wins, no contention model), PLUS a sticky "seen" bit: set at each falling edge (when TH is an input), cleared by the next `$DD` read (for each port whose TH is an input) and cleared at the wrap of every picture (tick 600 of the last line, the sync site of decision 5(d)), so a read shows TH low at least once per light pulse and a pulse never outlives its own picture. Evidence: MAME (`lphaser.cpp` turns TH low at the first bright sample and `sms_m.cpp` latches on the TH rise: `sms_ctrl1_th_input` calls `lphaser_hcount_latch` when TH goes 0 to 1) and ares (`cpu/memory.cpp:242`) latch on low to high only; SMS Power says latch when TH goes active (low) and that the return to 1 does not re-latch; MacDonald says the latch value is the H at a TH change of either edge. Three sources, three rules, no hardware measurement: the project follows the one that plays the 13 flagged dumps (MAME) and does not claim it for hardware (DEC.15); it also keeps every shipped latch position, which the unchanged-proof demands. Where MAME and this model AGREE and where they do NOT (re-read at the pin: `lphaser.cpp:213-221`, `bright_aim_area`): MAME keeps the sensor on, once on, "until out of the aim area" and re-checks at `aim_area.max_x + 1`, the chord end of the aim disc, not at the end of the lit run; so MAME's release (and its latch) is at the chord end plus one dot whatever the picture holds. For a uniformly bright area (the frames Phaser games draw for the shot) the pixel-following rule below ends the run at the same dot and the two agree; for a lit shape smaller than the disc (the fixture's 16 dot square aimed at its right edge) this model releases at the first non-lit dot and MAME would release up to 6 dots later. Agreement with MAME is therefore claimed for bright frames only; pixel-following is kept because GUN-01 says "emitted pixel" and the fixture's closed form depends on it, and the fixture adds one full-width band row (decision 10) where both rules coincide, so a local judge can separate an edge-rule error from a shape-rule error. The seam is one predicate in `th_edge`, so a local judge that shows another rule is a one-line change. Why sticky: a lit run of 13 dots is 26 ticks, 8.7 Z80 cycles, while the cheapest TH poll loop (`in a,($DD) / bit 6 / jr`) takes 25 to 31 cycles, 75 to 93 ticks; a purely geometric TH is missed on most lines, and loops whose length divides the 228-cycle line (114 and 228 cycles) sample one fixed column and would NEVER see a narrow pulse. MAME has a bit with the same purpose (`th_latch`, for two named titles: Color and Switch Test, Hang-On and Safari Hunt) but it is NOT the same bit and its rules differ (re-read at the pin): in MAME it is the ONLY way TH reads low on `$DD`; it is set at each falling TH while TH is an input (`sms_m.cpp:30-60`); a `$DD` read shows TH low only if the bit is set AND the VDP's `hcount_latched()` is true, and clears the bit whether or not it showed (`sms_m.cpp:309-317, 330-338`); `$7F` clears `hcount_latched` on every read (`315_5124.cpp:447-450`) and the end of the last top-border line clears it again (`:684`). So in MAME a poll between the fall and the release reads TH high, a pulse shows once and only after its latch, and a `$7F` read hides it. This model does NOT port the gate: `hheld` never clears here, so the gate would be a no-op (a literal port would only look like MAME), and the pin is level-sensitive on the hardware (MacDonald), so the readback is the live level OR the sticky bit, ungated by the latch. The wrap clear is the substitute for MAME's top-border clear: it bounds the bit's life to the picture in which the pulse happened (a title that reads `$DD` only after VINT, as Color and Switch Test does, still sees every pulse of the picture, since VINT, at line 192, 224 or 240, is before the wrap on all three heights) and approximates MAME's clear; `docs/controllers.md` says so. The `$7F`-read clear stays a deferred idea. The bit has no other effect: the latch and the edge rule use the geometric level only. How the GUN-04 fixture settles what it can: it reads `$7F` right after seeing TH low (value A) and again after TH has returned high (value B), at ten loop lengths; the model gives A = B because a read takes at least 22 Z80 cycles after the poll, longer than any pulse, so both must equal the closed form of the RELEASE edge (decision 4); a leading-edge latch would give a different, row-dependent value and fails the row. What no automated run can settle, stated plainly: the true latch edge, the true delay, the pulse width and whether the sticky bit is hardware are model-derived from emulators and UNMEASURED (DEC.15). A local-library run by the agent (Shooting Gallery, Gangster Town on both ports, Operation Wolf, Space Gun, Missile Defense 3-D with `--eyes`, Color and Switch Test, Hang-On and Safari Hunt, Laser Ghost: scripted aim at a known on-screen target with a trigger, judged by a RAM change or a `--png`) could change `GUN_DELAY_TICKS`, the sticky bit or the edge predicate and nothing else; it goes on the SEED-010 hand-off list in the close plan and is not a gate.
4. **Constants and the tick, pixel and H arithmetic.** `GUN_DELAY_TICKS 38`, `GUN_RADIUS 6`, `GUN_LUMA 127`, weights 77, 150, 29. All named once in `src/internal.h` with MAME as the cited default and "unmeasured" in the comment; no number appears in a test, fuzz seed or doc except through its name or a derivation.
   - Dot x (0..255) of a line is emitted during ticks `[2x, 2x + 2)` of that line (tests pin `hcount(0) = 8`, tick 559 -> `$93`, 560 -> `$E9`; `H(2x) = 8 + (x >> 1)`). The sensor sees dot x `GUN_DELAY_TICKS = 38` ticks later (19 dots, 12.67 Z80 cycles, 3.54 us; MAME's default offset 19 is the mode and median of the 14 per-title values 9..22, and 38 ticks is that value times two). The delay applies to BOTH edges, so TH falls at `2 x_on + 38` for the first sensed-lit dot and rises at `2 x_off + 38` for the first dot after the run that is not sensed-lit (a dark dot, outside the disc, or the end of the field at dot 256).
   - Latched H = `vdp_hcount_at(2 x_off + 38)`. For x_off <= 256 the tick is at most 550 and `550 + 32 = 582 < 592`, so the 340 jump is never reached on either TV (the line is 684 ticks on both), and `H = (2 x_off + 70) >> 2 = (x_off + 35) >> 1`. Example: a lit run ending at dot 135 (x_off 136) latches `(136 + 35) >> 1 = 85` (`$55`).
   - `vdp_hcount_at(t)` is the existing formula as a pure function of the in-line tick; `vdp_hcount(m)` becomes `vdp_hcount_at(m->bus.t)` and `vdp_latch_h(m)` stays its `_at(bus.t)` wrapper (one caller, no test calls `vdp_latch_h`), so every shipped latch position is bit-identical by construction and the whole `tests/io`, `vdp`, `bus` and `ports` latch families stay byte-equal.
   - Sensed region: the integer disc `dx*dx + dy*dy <= GUN_RADIUS*GUN_RADIUS` around the aim dot, clipped to the field. Row widths for dy 0..6 are 13, 11, 11, 11, 9, 7, 1 dots (113 dots in all, 13 rows); MAME's `ceil(sqrt)` shape has 133 dots, differs by at most one dot on six rows and is not used (the first-lit dot of a row moves at most 1 dot, half a H count). Every dot is tested (MAME samples every 4th dot and quantises the first-lit position up by 0 to 3 dots; the per-dot scan is exact and still tiny). Half widths are computed by a loop of at most six steps, not a table. "No `const` arrays in `src/gun.c`" is a rule chosen for this file so that a per-title table cannot hide there, enforced by `policy.no_title_table` (decision 10); it is not a core-wide rule (`synth.c`, `crc32.c`, `cart.c` and `io.c` hold `const` arrays) and no comment cites XFER-071 for it.
   - Aim conversion, stated once: an aim `(ax, ay)` is 1-based and the dot is `(ax - 1, ay - 1)`; every "dot" below, in the scanner, the tests and the fixture, is that 0-based dot, and every value passed to `set_input` or written in a script is dot plus one.
   - Lit: `(77 r + 150 g + 29 b) >> 8 >= 127` on the 8-bit expansion `n * 17` of each RGB444 nibble of the finished field pixel (the sensor reads `field[y][x]`, never CRAM). Verified by enumeration of all 64 Master System colours: 32 are lit (MAME's float 0.299, 0.587, 0.114 at `$7F` lights 30 on its own palette); white, yellow, cyan, green, light grey (2,2,2) and (3,2,x) pass, grey (1,1,1), red, blue and magenta fail; the colours nearest the threshold are (1,2,0) = 125 and (3,1,0) = 126 (dark) and (0,2,3) = 128 and (2,1,3) = 129 (lit, blue heavy, where MAME's darker blue differs). The unit test pins those four boundary colours, so a changed weight or threshold fails by name. Game Gear 12-bit differs on 3 of 4096 values, not reachable (no gun there).
   - Tolerance for GUN-04: the core is exact (the unit tests allow 0); the fixture's Z80-visible rows allow plus or minus 1 H count (2 dots, 4 ticks). Derivation: one H count is the counter's granularity (`vdp.c` calls the sub-dot origin "a coordinate inference, not a measurement", so one count of convention is allowed and no more). The controls are all at least 3.5 counts away: a read-time latch is at least 16 counts late (a poll plus a read is at least 66 ticks after the edge), the leading edge is 3.5 counts early on the centre row, a delay of 8 counts more is 8 away, an aim 16 dots off is 8 away; the tolerance must fail all of them.
5. **Sensor design and hash neutrality.** Decision: a LAZY SCANNER in new `src/gun.c`, not a renderer or per-line hook (DEC.28: devices catch up lazily to the access stamp). It reads `m->field` and calls the renderer only as described below; it writes no pixel. State per port is the 24-byte block (decision 8). One entry point `cogmaster__gun_sync(m)` brings every phaser port's cursor up to the beam `(bus.line, bus.t)` by a TWO-WAY MERGE IN TIME ORDER; one wrap entry `cogmaster__gun_wrap(m)` re-arms. The merge (the H latch is ONE register, `vdp.c:260-263`, so with two guns the order in which edges reach it is observable, and Gangster Town's table row attaches a phaser to both ports by default): a port with `g_scan` set has a next dot `(g_line, g_dot)` whose sensor tick is `2 g_dot + 38` (the closing dot included); `gun_sync` repeats "take the port whose next dot has the smaller `(line, tick)`, a tie going to port 1, stop if that dot is after the beam, else process that one dot (flip the lit bit, `th_edge` at the dot's own tick, advance that port's cursor)" until no port has a dot due. It is the same bound (at most 113 + 13 dots per picture per gun, so at most 252 merge steps per picture, however often anything polls), and the processed order is the order of a poll at every instruction, so the latched `hcounter`, `hheld` and the block at any boundary do not depend on the poll schedule. A per-port sequential loop (port 1 to the beam, then port 2) is the wrong design: edges at tick 400 on port 1 and tick 300 on port 2 of one row, synced once at 500, would leave the later register value 300 where a poll at every instruction leaves 400. A tie (the same row and tick on both ports) latches one value whichever port goes first; the tie rule only fixes the order of the lit bits, and `docs/controllers.md` states it. Every call site is guarded by the same two loads, `m->input.port1 == PHASER || m->input.port2 == PHASER`, so with no phaser attached the cost is one predicted branch at four existing cold-ish sites and nothing at all in the per-line event path.
   - Sync sites (all already exist): (a) `chip_in` before `port_dd` (the `$DD` read; `$DC` carries TL only and needs none). The side effect on this read path, justified: `chip_in` is already not a pure read (it sets `input_read`, the lag bit); the sync and the clear of `seen` live in `chip_in` ONLY, as the console's own latch of the TH line (MAME's `th_latch` is console state cleared by the read, the same as `hheld` here), not device state. `port_dd`, `port_dc`, `cogmaster__ports_pins` and `th_pins` stay pure functions of the instance, so the `ports.c` header comment ("a read of $DC or $DD cannot move a device") stays true and is not edited, and `cogmaster_peek` (which never reaches `chip_in`) and any observation tool leave the block untouched; `ports.gun.peek` asserts that (a lit, scanned state: `cogmaster_peek`, `cogmaster__ports_pins` and `th_pins` leave the whole instance byte-identical, and a second `$DD` read after the first changes nothing more); (b) `vdp_read` HCOUNT, so the latch is current before `$7F` answers; (c) `io_control` before `m->io.io_ctrl = ctrl`, so edges up to the write use the old direction bits (a sensor edge and a CPU `$3F` write at the same tick order sensor first, a choice stated in `docs/controllers.md`); (d) the wrap, inside the existing `if (line + 1u == cogmaster__frame_lines(m))` of `cogmaster__vdp_event` (tick 600 of the last line), BEFORE the height update: finish the old picture's remaining rows, clear `seen` on every port, then re-arm; (e) the end of `cogmaster_run_frame` after `bus_run_frame`, INSIDE the `if (m->cart.rom != NULL)` branch (`frame.c:60-62`; the test-card branch has no beam and never calls `gun_sync`), so the cursor at a frame boundary is a function of the beam alone and the state at a frame boundary does not depend on the poll schedule.
   - Re-arm at the wrap: for each phaser port, snapshot the aim from `m->input` (`g_ax`, `g_ay`); if it is `0 0` the picture is not scanned (`g_scan = 0`); otherwise `g_scan = 1`, cursor to row 0. A fresh attach, a reset or a load has `g_scan = 0`, so no stale picture is ever scanned. Because `m->input` is set at the window start (line 192 tick 607) and the wrap is at tick 600 of line `frame_lines - 1`, the snapshot is always the aim of the frame in whose window the picture's first row is drawn; the rows 192 to 223 of a 224 line picture, scanned in the next window, still use it.
   - Scan: rows `y` in `[ay - 1 - 6, ay - 1 + 6]` that are below the picture height (the cursor jumps over the others in one step); per row, dots `n` from the chord start to the chord end plus one closing dot, each processed once, in order. A dot is PROCESSED only once its sensor tick `2n + 38` is at or before the beam (rows above the beam line: always), and only if the renderer has emitted it. At most 113 sensed dots plus 13 closing dots per picture and 14 per row, per gun, however often anything polls; a sync with nothing new is one compare chain. `samples` is counted in a non-saved `struct cogmaster__gun_stats {samples, syncs, edges}` (like `synth_stats`).
   - Rendering rule (the neutrality lemma, to be a test): the scanner asks for dots only up to `T/2` EXCLUSIVE of the current line (the same bound every VDP write uses) and never calls the renderer when `bus.line >= height` (all rows are final then: the line 512 event of line `height - 1` rendered them, and a call would flush the field early and reset the cursor). Rendering earlier is idempotent: every mutation renders `< t/2` first and the line event renders the whole line, so a pixel and every status flag come out the same. It never uses the status read's `T/2 + 1`. First-fault neutrality: when `display` is on and the mode is unsupported the scanner does NOT render (it waits for the renderer's own cursor), via one predicate exported from `vdp_render.c`; otherwise a gun could record the first fault at a different pc and dot (`fault.c` keeps the first, and the fault is saved state). Lag neutrality: the scanner never touches `input_read`, `open_bus_reads`, `bus.data` or `vdp_at`; `$7E`/`$7F` reads are not polls; `$DC`/`$DD` reads still are, exactly as with a pad.
   - Proof of "existing latch positions unchanged": the refactor in plan 2 changes no behaviour (it adds `vdp_hcount_at`, an old/new `th_pins` taking a sensor mask that is 0 with no gun, and `th_edge`), the unchanged-proof command prints exit 0 on `tests/io tests/vdp tests/bus tests/audio tests/testcard_pins.cmake tests/ports/test_ports.c`, and `ports.gun.latch_at` asserts `hcount_at(t)` equals the pre-refactor formula for t = 0..683 (negative control: an origin off by one fails).
   - Proof of "no per-line cost with no phaser": the diff adds nothing to `vdp_next_event` or the line branch of `vdp_event`; with no gun the stats are all zero after 3 frames of a polling program; the perf gate's `delta_bp` on `boot_to_play` stays at or under 100.
   - Bound proofs: a hammer (10^6 `$DD`, `$7F` and `$3F` accesses at one tick, then at every tick of a picture, aim over a lit square) leaves the block, `hcounter` and the render cursor unchanged after the first call and `samples` at most 126 per picture and 14 per row; schedule independence (a poll at every instruction against one per frame gives equal edges, latch and, at the frame boundary, equal block), for one gun AND for two: the two-gun case aims port 1 at x 150 and port 2 at x 100 on the same rows of a bright band, so on every row the later edge belongs to port 1 (release ticks `2 (ax + 6) + 38`: 350 against 250 on the centre row, and the same order on every disc row) with both edges inside one sync interval, and a single sync late in the band, or at tick 500 of its first row, must leave the same `hcounter`, `hheld` and block as a sync after every tick; controls: a merge that runs port 1 to the beam and then port 2 leaves a different `hcounter` on that case, a scanner that restarts the row at each call exceeds the bound, one that renders to `T/2 + 1` fails the same-tick-VRAM-write fixture, one that latches at the read tick fails the edge-tick test at three loop lengths, one that renders under the unsupported-mode predicate changes the fault record.
6. **GUN-02 "no shot": the invariant that is true.** The sensor responds to light whether or not the trigger is held (the hardware does; the Hang-On title screen reads H with no trigger), so a gun aimed at a lit area is NOT neutral for a program that reads TH or `$7F`. The true and testable invariant: a run with a phaser attached, the trigger never pulled (`p` bit 4 never set) and no light in the sensor's view (aim `0 0`, or aim over dark dots) has the same frame and audio hashes, the same lag and open-bus counters, the same fault record and the same saved state, apart from the gun's own fields, as a run with a pad and nothing pressed. Pins agree because the phaser's `ports_pins` returns `0x2F | (~held & 0x10)` (direction bits and `p` bits other than 4 are ignored while the gun is on the port) and a pad with nothing pressed returns `0x3F`. ## Implementation Decisions by requirement

### GUN-01: sense the emitted pixel, latch at the edge tick, no per-title table
- Pins (`ports_pins`): phaser = `0x2F | (~held & PIN_TL)`: TL is the trigger (`p` bit 4, low = pulled), D0 to D3 and TR undriven high, every other `p` bit and the direction bits ignored. TH is not a port pin: it reaches `$DD` b6 (port 1) and b7 (port 2) through `th_pins(m, ctrl, low_mask)`, which gains a sensor mask (0 when no gun, so `$DD`, the 256 by 256 latch differential and every pin differential are unchanged) and pulls a bit low only on an input TH. The edge detector and the readback share that one function, so the edge rule has one definition; the readback mask is `lit | seen`, the edge mask is `lit` only.
- `th_edge(m, old_pins, new_pins, tick)` is the single latch site: `if (~old & new & 0xC0) vdp_latch_h_at(m, tick)`. `cogmaster__io_th_changed` keeps its signature and its Phase 8 behaviour (old and new from `th_pins(.., 0)`, then `ports_th` per wire change) and calls it with `bus.t`; the scanner flips the lit bit, recomputes pins before and after, and calls it with the edge's in-line tick `2n + 38`. `ports_th` is never called for a sensor edge (it is not a console wire change).
- `chip_in` `$DD`: sync, read, then clear `seen` on each port whose TH is an input (the read reported it); the wrap clears it on both ports (decision 3). `seen` is set only at a falling edge on a port whose TH is an input, so an output TH never accumulates it. The side effect is in `chip_in` only, next to `input_read`, and is justified in decision 5(a); `port_dd` stays pure.
- `src/gun.c` is the one file for the model; hardware comments cite SMS Power Light Phaser, MacDonald section 11, MAME `lphaser.cpp` and `sms_m.cpp` and PITFALLS 9, and label each constant unmeasured. It contains no title, header, hash or `cart` reference (the check of decision 10 scans it).
- Tests (`tests/ports/test_gun.c`, closed-form on the internal API with draws by VDP writes, no assembler): `ports.gun.latch_at` (decision 5); `ports.gun.model` (an independent oracle in the test with its own disc test, own luma weights and own tick `2x`: aim x 0..255 step 17, y over 192, 224 and 240 rows, three lit squares, two regions; first edge tick, latched H and TH level at each tick equal exactly); `ports.gun.edge` (read `$7F` at E+1 .. E+683 after the release edge E: constant; the next row's release edge falls at E+684, and a lit shape whose next row ends at another dot would move the value inside a longer window, so the case uses the square with its vertical right edge and stops at E+683); `ports.gun.luma` (the four boundary colours, white, black and the 64-colour count 32); `ports.gun.control` (the oracle with delay +16, a read-time latch, the wrong edge and no sticky each disagree somewhere on the grid); `ports.gun.order` (a VRAM write at the same tick as a poll: the frame hash and field do not depend on the gun); `ports.gun.fault_neutral` (an unsupported mode, gun on, equal fault record to the no-gun run); `ports.gun.lag` (a frame that only reads `$7E`/`$7F` is lagged exactly as without a gun; one that reads `$DD` is not); `ports.gun.seen_expiry` (a pulse sets `seen`, no `$DD` read, the wrap passes, then a `$DD` read shows TH high; control: a build without the wrap clear reads low, and the same pulse with a read before the wrap shows low once and then high); `ports.gun.peek` (decision 5(a): `cogmaster_peek`, `cogmaster__ports_pins` and `th_pins` leave the instance byte-identical, and a second `$DD` read changes nothing more).

## Risks and what a reviewer should attack
- The edge rule, the delay and the sticky bit are emulator agreement, not measurement. Attack: does a local run contradict MAME on a title; a poll loop that never reads `$DD` but `$7F` in a loop (Hang-On and Safari Hunt's title screen) never gets a latch before the first release; `hheld` never clears, so the first lit row after power-on and every later row give the same frozen value (and MAME's latch gate, which depends on a clear, is not portable here; decision 3).
- The sticky `seen` bit makes a `$DD` read mutate state and show TH low once for a pulse that already ended. Attack: a read right after a `$3F` write that turns TH into an input while lit; two `$DD` reads in a row; the bit set while TH is an output (it must not be); a state with `seen` set and `g_scan = 0` (legal between the last lit row and the wrap); a poll after a long gap, which must not read TH low for a pulse of an earlier picture (the wrap clear); two guns whose edges interleave in one sync interval (the time-order merge).
- Aim canonicalisation: an aim of dot -1 (x or y 0) parks the gun; a title never needs it. Attack: x 256 and y 240 (accepted), 257 and 241 (parked), `(0, 5)` (parked by the core, exit 2 in the runner), INT32 extremes (`ERR_ARGUMENT`), tags 32, 36 and 48, and that a parked pending pair is stored as `0 0` in both records.
- Neutrality: the scanner calls the renderer. Attack: the same-tick VRAM write at `T/2` against `T/2 + 1`, an unsupported video mode with the display on (the fault record), a status read at the same tick, `line >= height` (no flush), the 224 and 240 line pictures that straddle two windows and a frame whose aim changes at row 192, a save at every tick of a frame loaded into a fresh instance and finished (byte-equal to the uninterrupted run), and a gun attached or detached mid-picture.
- A lit sensor at `$3F`: edges at the same tick order sensor first; a TH direction toggle while lit 10^6 times; the Japanese echo-0 rule (`th_pins` echoes 0 on Japan for an output TH; the sensor applies only to an input).
- Fixture honesty: the expected values are derived from the model's own closed form, so the fixture proves the Z80 sees the model, not that the model is right; the tolerance (plus or minus 1) is only meaningful with the controls; V is read live and judged as a range.
- Perf and bounds: the five guarded sites on `$DD`, `$7F`, `$3F`, the wrap and the frame end; `delta_bp` at the first hosted dispatch on the branch and on `main` (and at the ship gate); the 126 and 14 sample bounds under a hostile polling schedule; `tests/fuzz` size; state `MAX_FIELDS` headroom.
- Host: the crosshair must never reach `native`, the eye pictures or the library hash; `lr_button` is JOYPAD-only today, so Pause and Reset on a gun port 0 depend on the new START/SELECT mapping; a frontend that offers the `LIGHTGUN` row for a port whose option says `pad` reads nothing (documented); the one-frame lag of the rectangle across a mode change.
