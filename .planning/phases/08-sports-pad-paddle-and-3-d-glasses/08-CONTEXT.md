## Resolved conflicts (decision, evidence, reason)

1. **3-D glasses availability.** Decision: no `$3E` gate and no SMS1-only gate. The eye is recorded from writes to `$FFF8-$FFFB` on every Master System profile (SMS1, SMS2, any region) and is always 0 on the Game Gear. Evidence: MAME `sscope_w` tests no `$3E` bit (the cart-enable test only picks where the RAM copy goes); `SMS-SYSTEM.md:105` says "SMS1 only; works with the card slot disabled" and SMS Power says the adapter snoops the bus with the slot disabled; the register is write-only and readable only through the RAM mirror, so recording it changes no guest-visible value and no hashed byte. Reason against SMS1-only: the default `--machine auto` is SMS2, so hardware-literal gating would make every 3-D dump report nothing by default and ship the flicker the pitfall warns about; the profile choice would also be a trap for users with no hardware knowledge. Reason against the `$3E` gate: it has no hardware source, and a cart running its code has `$3E` b6 clear anyway. State this in `docs/controllers.md` as a modelling choice (real glasses exist on SMS1, Mark III and the Japanese SMS only; SMS2 reporting is a convenience, not a claim; the SMS Power sentence about the disabled slot is about the card slot, not the cartridge bit, and is not a source for SMS2). Known cost, stated: MAME wires `$FFF8` only in the SMS1 class and only with its `SSCOPE` option on, so MAME never reports an eye for a non-3-D title; here a title that writes the work-RAM mirror at `$FFF8-$FFFB` for its own reasons (a clear or fill loop, a variable placed through a mirror address) reports a non-zero eye. The core cannot tell them apart and the hash is untouched; the cure is host-side (decision 8: the adapter composes only after it has seen the eyes alternate) and the extent is measured once (decision 8, `--eyes` over the local library). Amendments, in the same commit as the code (Phase 7 SAVE-03 precedent): REQUIREMENTS PAD-04 becomes "The 3-D glasses eye written to `$FFF8-$FFFB` is reported with each frame's run result on every Master System profile and is 0 on the Game Gear, and the host composes the eyes outside the hashed frame"; ROADMAP criterion 3 becomes "The 3-D glasses eye is reported with each frame on every Master System profile whatever `$3E` says, is 0 on a Game Gear and when nothing wrote it, and the frame hash is the same whether or not the host composes the eyes (PAD-04)"; the research text "gated by the cartridge enable bit" and PITFALLS 12 ("`$3E`-gated hook test", "SMS2 and GG inert") are superseded. The "attached flag" in the research is dropped (nothing can detect the glasses).
2. **Which eye a frame reports.** Decision: a value computed during the frame and reported at frame end: `glasses_frame`. At frame start `glasses_frame = glasses` (the eye in force, the last write). A write to `$FFF8-$FFFB` sets `glasses`; it also sets `glasses_frame` when it lands before the middle of the active area, tested on the WINDOW-RELATIVE tick: `win = m->ticks - (m->bus.deadline - frame_ticks)` and `win < GLASSES_CUT_TICKS` with `GLASSES_CUT_TICKS = (frame_lines - 96) * 684 - 607` (`frame_lines` 262 or 313; the window is anchored by the deadline, so the constant is the same in the 192, 224 and 240 line modes). That is: the window start (line 192 tick 607), all of vblank, and the top 96 active lines count for this picture; the lower half of the active area, all of line 192 up to tick 606 at the window's end, and any overshoot past the deadline belong to the next picture. One 64-bit subtract and compare on a rare path, no divide. The cut at active line 96 is the core's own choice, documented in `docs/controllers.md`: MAME cuts at half the screen's TOTAL height (about active line 88 on NTSC, 86 on PAL, varying with the video mode), which is not claimed. The result's `glasses` is `glasses_frame`. This is MAME's rule (state at active start, overridden by a write in the top half) expressed in our window; a naive end snapshot inverts depth in MAME's frame, which ends after vblank, and in ours differs from the rule only for a write after the cut. Negative control: writes at active lines 20 and 150, at `win = CUT-1` and `win = CUT`, at window tick 0 and at line 192 tick 606 (end of window), on NTSC and PAL and in the 224-line mode; an end-of-window snapshot reports the late writes in this frame and the rule defers them. Encoding: `COGMASTER_GLASSES_NONE 0` (never written since load or reset), `RIGHT 1` (b0 = 0, right shutter open), `LEFT 2` (b0 = 1).
3. **Sports Pad timing.** Decision: implement the MAME rule only, evaluated lazily at the falling TH edge: if the sequence is at its second fall (step 2) and `tick - edge >= SPORTS_IDLE_TICKS 1536` (TH held high 143.03 us = 512 Z80 cycles, MAME `10,738,635/3/512`), the sequence restarts and latches. They are two different quantities (MAME: TH-high abandon; ares: TH-low dwell resync of 60 us = 644 ticks), and the nominal 80/40/40/40 us read satisfies both. The ares 644-tick resync is NOT modelled and is recorded as an unmodelled alternative; add it only if a local judge of the owner's three Sports Pad dumps shows a desync. Reason: no timer, no event, no catch-up on reads, one comparison at an edge; MAME is also the pin the project already follows. Paddle half-period: `PADDLE_HALF_TICKS 299`. Derivation: SMS Power and ares give the clock as 18 kHz; read as the TR frequency its half period is 10,738,635 / 36,000 = 298.3 ticks, MAME's `XTAL/3/100` is 300; ares as coded toggles every 596.6 ticks (a 9 kHz TR), which contradicts its own comment, so it is not used. 299 (13 x 23) is inside 0.4 percent of both candidates and is not a multiple of 3, so no whole-Z80-cycle polling loop of fewer than 299 cycles locks EXACTLY to it (a loop of N cycles advances the phase 3N mod 598 per sample and 3N is never 0 mod 598 below N = 299; 300 locks at a 200-cycle loop: 0 or 100 percent ones, the PITFALLS 10 failure). A NEAR-lock exists: N = 199 advances the phase by 597, that is -1 tick per sample, so a 256-sample count spans under half a period and its ones ratio can be 0 to 100 percent; N = 398 is the same. No known title polls at those lengths; this is documented in `docs/controllers.md` and the sweep reports 199 and 398 as documented near-lock rows OUTSIDE the pass criterion. The fixture sweep decides, not taste: the constant is kept only if every swept length in {29, 31, 47, 64, 97, 100, 101, 200} gives 30 to 70 percent ones. Both constants are defined once, by name, in `src/internal.h`; no test, fuzz seed or doc number repeats 299, 598 or 1536 except through the name, so a sweep that moves the constant edits `internal.h` and `docs/controllers.md` only. TR = `(ticks / 299) & 1`, origin tick 0, both ports the same phase, no state. If `abi.globals` rejects the 64-bit divide on a lane, reduce `ticks` with 32-bit arithmetic (`fm_in` is the precedent).

   **Delta sign.** Host convention: +x right, +y down (mouse and stick). Sports Pad: the pad byte is the NEGATED host delta, X and Y (MAME `PORT_REVERSE` and ares `-x` agree; this is emulator agreement, not hardware proof, and a self-authored fixture can only prove the core against itself). Paddle: position = clamp(position + x, 0, 255), +x clockwise = larger (SMS Power: 255 is fully clockwise); `y` is ignored on a paddle. A sign error could only show on the owner's three Sports Pad and four Paddle carts, judged locally (see Defaults); a wrong sign is a one-line fix. Do NOT ask the owner now.
   **Where deltas live.** `pending_input` accumulates: each `set_input` adds its axes as `pending = clamp(pending + d, -32767, 32767)` per axis. Each addend is already inside +-32767 (range check) and so is `pending`, so the sum is inside +-65534 and fits `int32_t` with no saturating intrinsic and no signed overflow; the stored value never leaves the state bound below, so a save after any number of calls loads. Buttons and devices are last-wins; two calls before one frame equal one call with the sum when |sum| <= 32767 (the test states exactly that, and a second case shows two +20000 calls give +32767). If a call changes a port's device the pending axes of that port restart from 0, and axes for a device that takes none are dropped, so pending axes are non-zero only for a selecting device (a state invariant). At frame start in `run_frame`, `cogmaster__ports_frame(m)` runs before `m->input = m->pending_input`: a port whose pending device differs from `input` device has its device block zeroed; then Sports Pad `acc[i] = clamp(acc[i] + pending, -1023, 1023)` (eight full read bytes; a pad that is not read does not hoard more; the operands are inside +-1023 and +-32767, so the sum fits), Paddle `pos = clamp(pos + x, 0, 255)` likewise; then the pending axes and `m->input` axes are zeroed (`m->input` axes are always 0, visited as range 0..0). Hostile `INT32` values are refused at range check. Replays record the per-call axes. Reset: device blocks and the glasses eyes are zeroed in `cogmaster__io_reset` (called by `boot_handoff` on load and on both reset kinds), which is also where the tick-stored edge is cleared, because `bus_origin` sets `ticks = 0` and `ticks - edge` would underflow; pending axes survive a soft reset (a delta sent just before a reset applies at the next frame; stated in `docs/controllers.md` and pinned by a test so a refactor cannot change replay behaviour), load zeroes them (existing `instance.c:239`). Zero state is valid for every device (paddle stores `pos ^ 0x80`, so zero is centre).

### Sports Pad and Paddle (PAD-02, PAD-03)
- State: `struct cogmaster__port` x2 as a member of `struct cogmaster` (not inside `io`, which stays small and keeps its tripwire): `uint64_t edge` (tick of the last TH wire rise), `int16_t acc[2]`, `int8_t val[2]`, `uint8_t step` (0..4), `uint8_t pos` (paddle position XOR 0x80); 16 bytes, `_Static_assert(sizeof == 16)` and a field-sum assert (the u64 pads differently on i386 and wasm32); `struct cogmaster__io` grows by the two glasses bytes (9 to 11, the assert in `state.c:61` follows).
- Sports Pad machine (all in `ports_th`, O(1), no loop, no timer): fall edge: `if (step == 2 && tick - edge < SPORTS_IDLE_TICKS) step = 3; else { d = clamp(acc, -127, 127); acc -= d; val = -d; step = 1; }`; rise edge: `step 1 -> 2`, `step 3 -> 4` (other steps unchanged), `edge = tick` on every rise. Because the wire alternates, a fall arrives only at steps 0, 2 or 4 (steps 1 and 3 are reached by a fall, so the next edge is a rise); the guard on step 2 is therefore the only one needed, and a "restart at step 1 or 3" attack is unreachable (a unit test asserts `ports_th` is called on alternating levels only). After a reset the first fall runs the else branch with `edge` still 0 (`step 1`, `val` possibly non-zero, `edge == 0`): a legal state. Output nibble on D0-3: step 0 `$F`, step 1 hi(val[0]), 2 lo(val[0]), 3 hi(val[1]), 4 lo(val[1]) (direct bits, X then Y); TL/TR are buttons 1 and 2 from `p` bits 4 and 5, active low; the direction bits of `p` are ignored while the device is on the port; both axes are latched at the sequence's first fall (a read sequence is about 300 us, far below a host frame). NTSC ticks on both TVs (the pad's own clock is not the console's; 0.9 percent on PAL, no title is sensitive).
- Paddle: D0-3 = nibble of `pos` (TR = 0 low, 1 high), D4 = button from `p` bit 4 active low, D5 = TR clock; a console TR output still overrides D5 through `tr_pin`. Both ports share the phase. The export-region "paddle" path needs no model: a Japan paddle never exists on export, and the title's own region test takes the TH path there (the fixture checks this).
- Tests (all closed-form in C on the internal API, no assembler): tick cases at `SPORTS_IDLE_TICKS - 1` and `SPORTS_IDLE_TICKS` (phase kept/reset), the phase walk, the clamp at +-127 with remainder across frames and the +-1023 cap, the pending clamp and sum rule of decision 8, device change resets that port, soft reset and load zero the blocks and the edge (no underflow), soft reset keeps pending axes and load zeroes them, paddle position saturation, the same bytes on Japan and export profiles (the WIRE value is used, not the echoed readback), poll hammer (10^6 reads and `$3F` writes at equal ticks leave the block unchanged and bounded work), refusal statuses, a state saved at step 1 right after the first fall of a reset instance (edge 0) that loads into a second instance and saves byte-equal. The fixtures (plans 11 and 12) add the Z80-side proof: `tests/roms/src/sports_pad.asm` (cycle-counted waits 286/143/143/143, injected deltas +5/-3, +127/-128 saturated, a >127 burst carried across frames; decoded bytes equal the NEGATED scripted sums, expected values computed by `math()` from the same literal list, never read from the core; abort after X-high then idle `SPORTS_IDLE_TICKS - 1` ticks keeps the phase and `SPORTS_IDLE_TICKS` resets it) and `paddle.asm` (the `in/bit/jr/inc/djnz` detect loop at 43/44 cycles and lengths 29, 31, 47, 64, 97, 100, 101, 200: ones ratio 30 to 70 percent at every length, plus 199 and 398 reported as documented near-lock rows outside the criterion; then the wait-TR-0/TR-1 reader reconstructing the position from the scripted sum). Negative controls: a frozen TR gives 0 or 100 percent and fails; `--port1 pad` on the paddle image fails the ratio rows; one scripted delta dropped moves a sum outside its row (`expect_fail`, regex `outside its row`). No frame hash is pinned from the core for these (a pin from the core passes its own bugs): the pins are the mailbox rows derived from the script plus cross-lane equality through `hashes.cmake` rows (`playing ...` lines, no audio rows).
- Replay (PAD-03): a test program records the per-call deltas of a library run, prints its frame hash; a cmake case replays the script through `cogmaster-run --input --hash` and compares; control: one delta off by 1 gives a different hash; and `state_equal`: run N frames, save, restore into a second instance, finish both, equal hashes and state bytes; the same total motion cut into different per-frame chunks differs (the deltas matter).

### State bounds and fuzz (PAD-07)
- `state.c` visits, after the input records (the cross-checks read visited devices; `io_io` runs before the inputs today, so the port blocks get their own call after the input block), and uses the VALUE the `sio_*` call returns, never `e->cmd`-style staged fields (the Phase 7 WR-01 lesson). New helpers in `state.h`: `cogmaster__sio_i32`, `_i16`, `_i8`, each the `sio_i64` XOR-bias trick at its own width (value 0 encodes as the top bit set: `00 00 00 80` for i32). **Field names and bounds (no name begins `input_`: `tests/io/input_cases.h:109-119` writes byte 255 into the first byte of every field whose name starts `input_` and requires a refusal, which a biased axis would accept as +255):**

  | Field (per axis or per port) | Type | Bound |
  |---|---|---|
  | `pending_x1`, `pending_y1`, `pending_x2`, `pending_y2` (the axes of `m->pending_input`) | i32 | -32767..+32767 |
  | `active_x1`, `active_y1`, `active_x2`, `active_y2` (the axes of `m->input`) | i32 | 0..0 |
  | `input_port1`, `input_port2` (existing names, both records) | u32 | upper bound 1 becomes SPORTS_PAD (one constant shared with `set_input`) |
  | `port_edge` | u64 | 0..`time.ticks` |
  | `port_acc` | i16 | -1023..+1023 |
  | `port_val` | i8 | -127..+127 (-128, two's-complement 0x80, refused) |
  | `port_step` | u8 | 0..4 |
  | `port_pos` | u8 | 0..255 |
  | `io_glasses`, `io_glasses_frame` | u8 | 0..2 |

  Cross-checks, each derived from what the core can produce (no rule here that a run, a reset, a load or the fuzz cannot reach):
  1. Every device in `pending` and `input` passes `device_ok` on the instance (a Game Gear holds only PAD or NONE; a PADDLE needs a Japan region; the profile is fixed by the header, so this is the availability rule).
  2. A port's block belongs to the device in force, `input.port_i`: PAD or NONE implies `edge`, `acc`, `val`, `step` and `pos` are all zero; SPORTS_PAD implies `pos == 0`; PADDLE implies `edge`, `acc`, `val`, `step` all zero (`ports_th` acts only on SPORTS_PAD).
  3. `step == 0` implies `val == 0` (`val` is written only by a fall, which sets `step` to 1; `acc` may be non-zero at step 0, it accumulates at frame start).
  4. Pending axes belong to the device in `pending`: PAD or NONE implies both axes of that port are zero; PADDLE implies `y` is zero; SPORTS_PAD is unconstrained.
  5. `glasses_frame != 0` implies `glasses != 0`, and both are 0 on a Game Gear.

  No `edge`-versus-`step` rule is added, on purpose: after a reset the wire is high, `edge` is 0, and the FIRST fall runs the restart branch (`edge` unchanged), so `(step 1, val non-zero, edge 0)` is a state the core produces and the first version of this rule ("`edge == 0` implies `step == 0`") would have refused it; a rise at tick 0 through the internal API (the fuzz does this) gives `(step 2, edge 0)`, so "`step >= 2` implies `edge > 0`" is not safe either. Every `(step, edge)` pair with `edge <= time.ticks` is reachable and the only use of `edge` is a subtraction that the first bound keeps non-negative.

  The new byte-mutation test (`tests/ports/test_state.c`, runs the record of `cogmaster__state_record`): on instances with each device attached and mid-sequence (SMS2 export Sports Pad at step 2 with non-zero `acc`, `val` and pending axes; SMS2 Japan Paddle with non-zero `pos` and pending x; Game Gear; glasses 1 and 2 with a different `glasses_frame`), for EVERY byte of EVERY new field above and each value in {0x00, 0x01, 0x7F, 0x80, 0xFF, the complement of the byte}: patch, reseal, load. A refusal must leave the instance byte-identical (`memcmp` against the pre-load snapshot); an acceptance must satisfy an independent bounds checker (shared with `fuzz_pad.c`, not with `state.c`), `save` after `load` must equal the patched bytes, and one frame must run. A table of just-outside values per bound (`pending_x1 = 32768`, `acc = 1024`, `val = -128`, `step = 5`, glasses 3, and each cross-check violated once) must be refused. `state.record_sweep` already mutates every bounded field out of range, but only on populated blocks; it is also run on instances with each device attached. Added: a state saved mid-sequence (steps 1 and 2) loads into a second instance and saves byte-equal; a same-profile state patched to `input_port1 = PADDLE` on an export instance (record, patch, reseal) is refused by the availability cross-check (a Paddle state saved from a Japan run is already refused by the header's region, which is why the test crafts a same-profile state). Negative control, run once by the agent and recorded: remove the `port_acc` bound and the mutation test fails.
- `tests/fuzz/fuzz_pad.c` (seeds in `seeds.c`, `fuzz.regress.pad`, `fuzz.libfuzzer.pad`; inventory lines `ci` and `wasm32` for `fuzz.regress.pad`, `fuzz` for `fuzz.libfuzzer.pad`; the `nofp` lane registers no fuzz test): op byte selects `set_input` (device ids and axes from an adversarial table: 0, 1, -1, 127, 128, 255, 32767, 32768, INT32_MIN, INT32_MAX and a raw stream word), `$3F` write (all 256 values), `$3E` write, `$DC/$DD` read, `$FFF8-$FFFB` write, tick advance (0, 1, `SPORTS_IDLE_TICKS - 1`, `SPORTS_IDLE_TICKS`, +1, up to 2000), reset soft or power, and `run_frame` (at most 4 per input), on a profile chosen by the first byte (SMS2 export, SMS1 export, SMS2 Japan, GG); refusals are expected statuses, an unexpected OK on an illegal device aborts. After every op one `check_pad()` (a second independent implementation of the table and cross-checks above, not shared with `state.c`) asserts the bounds. The WR-01 leg: take a valid save, mutate 1 to 3 device or input fields through `cogmaster__state_record`, seal, `state_load`; if it returns OK the invariants must hold and save, load, save must be equal and one frame must run; if it refuses the instance must be byte-identical to before. Fuzz total stays under the 524,288-byte budget.

## Risks and what a reviewer should attack
- The Sports Pad sign and the Paddle direction are emulator agreement only; both can only be refuted on the owner's carts (a local run, a one-line fix). Attack: does a later judge contradict MAME and ares?
- The 1536-tick rule alone may desync a title that waits less than 80 us or that never leaves TH high 143 us after an aborted sequence; the ares 644-tick resync is the named fallback. (An abort at step 1 or 3 followed by a short TH-high gap cannot occur: falls arrive only at steps 0, 2 and 4.)
- `PADDLE_HALF_TICKS 299` is not a number in either source. Attack: the loop-length sweep, the documented 199 and 398 near-lock, and a title whose own loop is a multiple of 598 ticks; the 64-bit divide on every lane (`abi.globals`).
- The glasses rule samples at active line 96 of a window that starts in vblank, on the window-relative tick. Attack: a write at `CUT - 1` versus `CUT`, a write at line 192 tick 606 versus 607, PAL (frame length differs, `GLASSES_CUT_TICKS` follows `frame_lines`), the 224-line mode, and the SMS2-reports choice (a reviewer may prefer hardware-literal SMS1; the documented answer is the default-profile usability argument, with the adapter's stereo rule and the measured false-positive count as the mitigation).
- `set_input` accumulate versus last-wins: a host that calls `set_input` several times per frame with the same absolute motion would double it (documented: deltas are per call, hosts send each increment once); the sum clamps at +-32767; a device change mid-window drops that port's earlier pending motion.
- Behaviour 14 and the Woody Pop region change: a reviewer should check no other row has region 0 with a paddle default except that dump and that `region_guess` is the only thing that moves.
- Over-read: the poison test depends on every appended field being range-checked so a read of 0x7F bytes is visible; adding an unchecked field later weakens it (the ASan exact-malloc case is the independent proof).
- State: a block that is zero but device-selected (valid) versus a non-zero block with PAD (refused); the visitor must use returned values; the byte-mutation test and the fuzz leg are the guard against a loader that accepts what no run produces and against a cross-check that refuses what a run produces (the first draft of this context had one).
- Budget attacks: the existing-test changes are exactly the table in decision 5 and `tests/cart/test_cartdb.c`; `tests/io`, `tests/testcard_pins.cmake` and `tests/audio` must show no diff; the counted check-code delta must print at most 12 more lines; `embedding.md` must stay at least 2 KiB under its cap.
- Hosted: the perf gate sees the `bus.c` change and the edge detector at dispatch 1 (right after plan 4); wasm32 and MSVC see the struct growth at dispatch 1; no lane may be first-run at the end.
