# Technology Stack: milestone v2.0 "The whole library"

**Project:** cogmaster
**Researched:** 2026-11-09
**Scope:** only what the v2.0 features add or change. The v1.0 stack (C17, CMake 3.25+ presets, Ninja, CTest, WLA-DX 10.7, SingleStepTests, emu2413 oracle, Valgrind, wasmtime 48, RetroArch 1.22.2, release-please) is settled and not re-researched.
**Overall confidence:** HIGH for "no new dependency"; MEDIUM for the `.srm` byte layout (to be measured, see Open Items).

## Verdict

**v2.0 needs zero new runtime dependencies, zero new vendored files and zero new language or build tools.** Every new capability is either (a) an extension of a mechanism that already shipped in v1.0, (b) roughly 100 to 400 lines of own C written from a public datasheet or a BSD-3/ISC file that may be read, or (c) a POSIX sh, `gh` and `jq` script in the pattern already used by `scripts/`. The two things that deserve real attention are not libraries: the hash table is 557,877 bytes today and will grow, and `docs/compatibility.md` cannot carry 1,476 rows under the 40,960-byte docs budget.

**Two generator traps found by reading the XML (HIGH):**

1. **EEPROM entries carry no `battery` feature.** The 7 `slot=eeprom` Game Gear entries have no `<feature name="battery">`, so today's `f.persistence` default (1 = none) would classify them as volatile and the save path would silently do nothing. The generator must set persistence from `slot == "eeprom"`, not from the battery flag.
2. **Unknown slot currently becomes board 0 without an error.** Keep that behaviour (unsupported board must stay refusable) but make the generator print a count per slot value on stderr so a new MAME slot appearing at a future pin is visible, and add a test that every slot in the pinned lists is either mapped or on an explicit "unsupported by design" list.

**Table size: compact it (MEDIUM-HIGH, measured).** `struct cogmaster__cart_fact` is 336 bytes per row (41-byte hex SHA-1, 256-byte title, nine `uint32_t`). `size build/library/libcogmaster.a` shows `cartdb.c.o` at **557,877 bytes** of read-only data for 1,657 rows; the average title is 33 characters, so about 75% of each row is title padding. Handhelds and wasm32 are stated targets and `size.zip` and `size.wasm` are ceilings in the planned `quality.json`. Recommendation, in this order:

1. Emit the SHA-1 as 20 binary bytes (`memcmp(…, 20)`), and pack the facts into `uint8_t`/`uint16_t` fields. About 40 bytes a row gives roughly 66 KB for the same rows.
2. Move the title out of the library: only `scripts/compat-common.sh` reads it (it greps `src/cartdb.inc` for `,1u},` rows). Generate a second file for the ledger side (for example `tests/compat/catalog.csv`) from the same generator run, and drop the title column from `src/cartdb.inc`. If a host-visible title is wanted later, use one string pool with 16-bit offsets (about 55 KB), not 256-byte slots.
3. Keep binary search. 1,657 rows take about 11 comparisons; a perfect-hash generator (gperf, CHD) saves nothing measurable and adds a build tool.

Do this in the first phase that touches `cartdb`, because the Korean boards add enum values to every row and the row layout is touched anyway. The change is covered by the existing `cart.database` and generator tests.

### EEPROM (93C46) and the save path

| Technology | Version | Purpose | Why | Licence |
|---|---|---|---|---|
| Own `src/eeprom.c` (about 100 to 150 lines): 93C46 Microwire state machine, 64 x 16-bit words | in-repo | Majors Pro Baseball, World Series Baseball (v0, v1), WSB '95, Pro Yakyuu GG League, GG League '94, Nomo's WSB | The chip's protocol is a public datasheet (Microchip 93AA46/93LC46/93C46 family, 1 Kbit, x16 organisation): start bit then 2-bit opcode: READ `10`+A5..A0, WRITE `01`, ERASE `11`, and the `00` group for EWEN (`11xxxx`), EWDS (`00xxxx`), ERAL (`10xxxx`), WRAL (`01xxxx`). Erased state is `$FFFF`. The bit-banged cart wiring is in `SMS-CARTRIDGES-AND-PERIPHERALS` 2.2 (read `$8000`: b0 = DO; write `$8000`: b0 DI, b1 CLK, b2 CS). | own code |
| MAME `src/devices/machine/eepromser.cpp` and `.h` as a cross-check | pin `1d7a454ed79e` | Read the state machine's edge cases (clock-edge sampling, write-busy handling) and use as a test oracle | Both files carry `license:BSD-3-Clause`, holder Aaron Giles (header read 2026-11-09 via `gh api`). It is C++ device glue; a line-for-line port saves little over own code, so treat it as reference, not seed. If a port is later preferred, `PROVENANCE.md` section 4 needs a seed row first. | BSD-3-Clause |
| Existing battery API (`cogmaster_get_battery`, generation counter) | in-repo | Persist the 128-byte image through the same span the host already knows | `cogmaster__battery_length` today requires `persistence == BATTERY`; add one EEPROM branch that returns 128 and bumps `generation` only when a WRITE, ERASE, WRAL or ERAL actually changes a word while writes are enabled. No new public function; the header (8,332 of 24,576 bytes) only gains one persistence constant. | MIT (own) |

Design points that keep the determinism rules:

- **No clock.** The datasheet's write cycle (milliseconds on a real part) is modelled as ready immediately or after a fixed number of emulated ticks. Both are deterministic; choose "immediately ready" unless a title polls DO and needs a busy phase (find out in the phase from the seven games' behaviour, do not guess).
- **State lives in the instance** and is serialised in the save state like every other device. Bound the opcode decoder to 6 address bits and ignore unknown opcodes (`SMS-CARTRIDGES-AND-PERIPHERALS` section 6).
- **Fuzz:** `tests/fuzz/fuzz_save.c` already exists; add the bit-banger as a target. No new fuzz tooling.
- **Word order in the file** is stored as 64 little-endian 16-bit words in the preparation recommendation. Serialise byte-wise (`lo`, `hi`) so the big-endian `be32` lane gives the same bytes.

Do not search for or open Genesis Plus GX or Gearsystem source to answer the `.srm` question. A web search for the 93C46 wiring returns a Genesis Plus GX `eeprom_93c.c` page; it is off limits.

**Likely consequence to plan for (LOW until measured):** other cores may write a larger `.srm` than the board's real RAM (for example a fixed 32 KB). The existing rule already handles the import direction (pad on import, never on export). If the measurement shows a mismatch, the only change is an import-side tolerance, never an export-side one, so no stack change.

**Runner `--save-dir`:** keep `runner/save.c` as is. The atomic-write machinery is complete and tested on POSIX, Windows and WASI. v2.0 adds only (a) the EEPROM span flowing through the same `cogmaster_get_battery` call, with no change in the runner because it already copies `length` bytes, and (b) a hosted save round trip test (already named in SEED-001) using the existing fault-injection hooks (`COGMASTER_SAVE_TEST`). Do not add a file-locking or directory-watching library, and do not add a `.sav` or `.eep` second file: one `.srm` per title, as RetroArch does.

libretro `.info`: set `libretro_saves = "true"` when the save path is wired, and drop `is_experimental` only at the last ledger phase. Each `true` already needs a test in `tests/cmake/repository.sh`.

### PAL and Japanese FM profiles; the ledger over the CC0 lists

No library. These are profile fields and test data on the existing tick lattice (`SMS-SYSTEM.md`). Two tooling constraints are real and measured:

1. **`docs/compatibility.md` cannot list every row.** It is generated by `scripts/compat-common.sh docs` and today prints the full row table. `tests/cmake/budgets.cmake` caps every `docs/*.md` at 40,960 bytes. At about 300 bytes a row, 1,476 rows are roughly 440 KB. Change the generator to print counts per machine/mapper/status plus only rows that have accepted evidence; `tests/compat/ledger.csv` (not under `docs/`) remains the full record. Do not raise the budget.
2. **Do not commit 1,476 `unknown` rows.** The coverage of "the ledger over the whole CC0 lists" is a count derived from `src/cartdb.inc` (every entry is identified), and rows in `ledger.csv` exist only where a predicate has been judged. This keeps `compat-common.sh` (101 lines of awk, input cap 4,194,304 bytes, counted against the one-tenth-of-`src/` check-code budget) inside its limits. If the ledger does grow, the existing 4 MiB cap is enough for 1,476 rows (about 0.5 MB).

`scripts/library.sh` (owner's private dumps, local only) already enumerates a flat directory and writes results under `build/`. Reuse it for the library-wide runs. Do not add a parallel runner, a database, or Python.

## Alternatives Considered

| Category | Recommended | Alternative | Why Not |
|---|---|---|---|
| Hash table lookup | Sorted array, binary search, binary 20-byte key | gperf, CHD or another perfect-hash generator | Another build tool for a lookup that already costs about 11 comparisons per load |
| Hash key | SHA-1 of the body | CRC-32 (MAME's other key) | 32 bits over 1,657 rows plus hacks; SHA-1 is already in the library and in every runner digest |
| Hash database source | Pinned MAME CC0 lists through `tools/cartdb.c` | No-Intro / libretro-database DAT files | Not clearly CC0 in the files read for this research; the MAME lists are CC0 by header and already pinned. Revisit only if an owner title is missing from MAME. |
| XML reading | The existing 311-line restricted reader | expat, libxml2, mxml | A dependency for a build-time tool that reads three trusted, pinned files; the restricted reader refuses entities and DTDs by construction |
| 93C46 | Own state machine from the datasheet | Port MAME `eepromser.cpp` (BSD-3) | C++ device glue; port cost approaches own-code cost. Keep it as the cross-check. |
| Save container | Raw `.srm` | A wrapper with header and checksum, or a second `.eep` file | Breaks swapping files with other emulators, which is the whole point of interop |
| Save atomicity | Existing temp + fsync + rename / MoveFileEx | A library (`libatomic_write`, SQLite, LMDB) | Already written, tested with fault injection on three platforms |
| Light-gun input | libretro `RETRO_DEVICE_LIGHTGUN` | Pointer device | The libretro lightgun device gives screen coordinates and off-screen state, which is the Phaser's need |
| Timeout and digest tooling | sh + `gh` + `jq` | A Python script, a GitHub Action marketplace package, a dashboard service | The house rule (POSIX sh or CMake `-P`), SHA-pinned actions only, and fewer moving pieces |
| Coverage floor | Defer | gcov + gcovr, llvm-cov in the tune-up | A whole lane for one number; gcovr is a Python dependency |
| Ratchet storage | One `quality.json` with `string(JSON)` | A metrics service or per-metric files | `ENGINEERING.md` section 8: one file, one check |

## What NOT to Add

- Any XML, JSON, SQLite, compression (zlib, miniz) or CSV library. Zip handling stays with the host (RetroArch unzips before `retro_load_game`; the runner takes a file).
- A Python, Node or Perl step in the build or in CI checks. The generator is C; checks are CMake `-P` or POSIX sh.
- Any code from Genesis Plus GX, Gearsystem, MEKA, BlastEm or any non-commercial or unlicensed source, including for 93C46 behaviour and `.srm` layout. Web results will offer it; do not open it.
- A second save file format, a save-state-in-`.srm` hybrid, cloud sync, or a `--save-dir` watcher.
- Window, audio-device or input-device code for the peripherals (rule 2). The core takes positions and deltas as input; hosts supply them.
- Coverage tooling, a benchmark dashboard, a merge queue, Codecov, Renovate or any of the YAGNI list in `ENGINEERING.md` section 7.
- New pins. The MAME pin stays; the `.srm` measurement uses released binaries once and leaves no pin.
